Что такое сетевые интерфейсы

Сетевой интерфейс — это программно-аппаратная точка подключения устройства к сети. В контексте Linux-сервера (а большинство VPS работают именно на Linux) интерфейс — это виртуальное или физическое устройство, через которое пакеты отправляются и принимаются.

Каждый интерфейс имеет:

  • Имя — например, eth0, lo, tun0, wg0.
  • IP-адрес — может быть статическим или динамическим.
  • MAC-адрес — для физических интерфейсов.
  • Состояние — UP (активен) или DOWN (отключён).
  • MTU — максимальный размер передаваемого пакета.

Для VPN-сервера критически важно, чтобы все нужные интерфейсы были активны и правильно сконфигурированы. Ошибка в настройках может привести к тому, что клиенты не смогут подключиться, трафик будет теряться или маршрутизироваться неверно.

Основные сетевые интерфейсы на VPN-сервере

🔄 lo (loopback)

Внутренний интерфейс с IP 127.0.0.1. Используется для связи процессов внутри сервера. Всегда должен быть UP.

🌐 eth0 / ens3 / enp0s3

Основной физический (или виртуальный) сетевой интерфейс, через который сервер общается с внешним миром. Имеет публичный IP-адрес.

🔷 tun0 (OpenVPN)

Виртуальный интерфейс, создаваемый OpenVPN. Работает на уровне IP (TUN) или Ethernet (TAP). Через него проходит трафик VPN-клиентов.

⚡ wg0 (WireGuard)

Интерфейс WireGuard. Работает на уровне IP, имеет свой приватный и публичный ключи. Обеспечивает быстрое и безопасное соединение.

🔒 xray / v2ray

В случае с XHTTP + Reality отдельного интерфейса может не быть — трафик маскируется под HTTPS и идёт через основной интерфейс, но с особыми правилами маршрутизации.

Понимание того, какие интерфейсы создаются вашим VPN-протоколом, — первый шаг к успешной диагностике.

Команды для проверки сетевых интерфейсов

В Linux существует несколько утилит для просмотра состояния интерфейсов. Вот основные из них:

1. ip link — список всех интерфейсов

root@vps:~# ip link
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN mode DEFAULT group default qlen 1000
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode DEFAULT group default qlen 1000
3: tun0: <POINTOPOINT,MULTICAST,NOARP,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UNKNOWN mode DEFAULT group default qlen 500
4: wg0: <POINTOPOINT,NOARP,UP,LOWER_UP> mtu 1420 qdisc noqueue state UNKNOWN mode DEFAULT group default qlen 1000

Обратите внимание на состояние UP — это значит, что интерфейс активен.

2. ip addr — IP-адреса интерфейсов

root@vps:~# ip addr
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN group default qlen 1000
    inet 127.0.0.1/8 scope host lo
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP group default qlen 1000
    inet 45.67.89.10/24 brd 45.67.89.255 scope global eth0
3: tun0: <POINTOPOINT,MULTICAST,NOARP,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UNKNOWN group default qlen 500
    inet 10.8.0.1/24 scope global tun0

Здесь мы видим, что tun0 имеет IP 10.8.0.1 — это адрес VPN-шлюза для клиентов.

3. ifconfig — классическая утилита

Хотя ifconfig считается устаревшей, она всё ещё широко используется:

root@vps:~# ifconfig -a

4. ss -tulpn — проверка прослушиваемых портов

Это поможет понять, слушает ли ваш VPN-сервер нужные порты (например, 443 для XHTTP + Reality или 51820 для WireGuard).

Проверка маршрутизации и IP-адресов

Мало просто увидеть интерфейсы — нужно убедиться, что трафик идёт по правильным маршрутам.

Таблица маршрутизации

root@vps:~# ip route
default via 45.67.89.1 dev eth0 proto dhcp src 45.67.89.10 metric 100
10.8.0.0/24 dev tun0 proto kernel scope link src 10.8.0.1
45.67.89.0/24 dev eth0 proto kernel scope link src 45.67.89.10

Здесь видно, что трафик для сети 10.8.0.0/24 направляется через tun0, а весь остальной — через eth0.

Проверка доступности интерфейсов

Используйте ping для проверки:

  • ping -c 4 127.0.0.1 — проверка loopback.
  • ping -c 4 45.67.89.10 — проверка внешнего интерфейса.
  • ping -c 4 10.8.0.1 — проверка VPN-интерфейса.

Если пинг не проходит, возможно, интерфейс неактивен или есть проблемы с маршрутизацией.

Диагностика проблем с сетевыми интерфейсами

⚠️ Проблема

Интерфейс DOWN — проверьте, не отключили ли вы его командой ip link set dev tun0 down. Поднимите: ip link set dev tun0 up.

⚠️ Проблема

Нет IP-адреса — возможно, DHCP не сработал или статический адрес не назначен. Проверьте конфигурацию в /etc/netplan/ или /etc/network/interfaces.

⚠️ Проблема

Маршруты не добавляются — убедитесь, что в конфигурации VPN (OpenVPN, WireGuard) прописаны правильные push "route ..." или AllowedIPs.

⚠️ Проблема

Высокая потеря пакетов — проверьте MTU. Для WireGuard часто используют mtu = 1420, для OpenVPN — 1500.

"Самый частый источник проблем на VPN-сервере — неправильная маршрутизация. Всегда проверяйте таблицу маршрутов после изменения конфигурации."

XHTTP + Reality: маскировка на уровне интерфейсов

🔬 Как XHTTP + Reality работает с сетевыми интерфейсами

Технология XHTTP + Reality не создаёт отдельного виртуального интерфейса вроде tun0 или wg0. Вместо этого она:

  • Использует основной интерфейс (eth0) для отправки трафика, но маскирует его под обычный HTTPS.
  • Имитирует TLS-рукопожатие — DPI видит стандартный браузер Chrome.
  • Не оставляет характерных сигнатур — в отличие от OpenVPN или WireGuard, у XHTTP нет узнаваемых паттернов.
  • Работает на уровне приложений — вам не нужно настраивать дополнительные интерфейсы, всё происходит прозрачно.

Это означает, что вы можете проверить работу XHTTP + Reality, просто наблюдая за трафиком на eth0 и убедившись, что он выглядит как обычный HTTPS-трафик. Никаких подозрительных интерфейсов, никаких лишних маршрутов.
